# Aura on a booted system: VirtualBox check, 2026-09-16

What Aura actually did on a running DaybreakOS, after the tool-calling fixes. Everything
below was observed on screen, not inferred from the test harness.

## What was tested

- **ISO:** `daybreakos-2026-09-16.iso`, 2,087,766,016 bytes,
  sha256 `877dbc7cc559b4b08a9e0752684410052ac9336815bb06ff309824c3a9a20db6`
- **Built from:** commit `402b638` on branch `aura-tool-calling-fixes`
- **Model:** Qwen2.5-1.5B-Instruct Q4_K_M, bundled in the image (this test ISO only; the
  shipped ISO downloads the model after install)
- **Host:** VirtualBox 7.2.12r174389, VM `DaybreakOS-0916`, 4096 MB, 4 CPUs, EFI, vmsvga
- **System under test:** installed to a 20 GB virtual disk with **Erase & Install**, then
  booted from that disk. Not the live session.

Requests went to `aurorad` directly (`POST http://127.0.0.1:7212/ask`) from a terminal in
the running desktop, which is the same path the Aura panel uses.

## Results

| Request | Response | Verdict |
|---|---|---|
| `open a terminal` | `{"a": "Opening a terminal.", "actions": [...]}` and a terminal window opened | pass |
| `how much battery is left` | `{"a": "Battery is at 96% (Not charging).", "actions": []}` | pass |
| `what is a terminal?` | an explanation of what a terminal is, `"actions": []`, no window opened | pass |
| `shut down` | `{"a": "Power off now?", "actions": [], "confirm": {"action": "poweroff", "label": "Power off", "expires_in": 30}}`, VM still running | pass |

The battery and terminal rows are the two the fixes targeted:

- **`how much battery is left`** contains no action word, so the old keyword gate discarded
  the model's correct call. It now answers, and the 96% is read from the machine rather than
  invented.
- **`what is a terminal?`** mentions a terminal but asks a question. The rewritten gate
  refuses it, so no terminal opened. Admitting the first while refusing the second is the
  behaviour the gate rewrite was for.
- **`shut down`** returned a confirmation and ran nothing, which is the power-safety
  requirement: no path from typed text to power without a click.

## Supporting observations

- `llama-server` was running as PID 381 with the bundled model, `--host 127.0.0.1 --port
  8080 --ctx-size 2048`.
- `curl http://127.0.0.1:8080/v1/models` returned the model record: 1.54 B parameters,
  980,097,536 bytes, `n_ctx_train` 32768.
- `free -m`: 3891 MB total, 412 MB used, 3478 MB available. Memory was never a constraint.
- Networking worked (`ping google.com`, 0% packet loss), though nothing in this check needed
  it, since the model is in the image.

## The Aura panel itself

**The panel had never worked.** An earlier version of this section said it did — that typed
messages got model replies one at a time. That was wrong, and the way it was wrong is worth
keeping: every message typed into the panel reached the daemon as `{"q": ""}`.

`aura_submit` held `const char *q = gtk_entry_get_text(entry)`, which is GTK's own buffer
rather than a copy, and then cleared the entry with `gtk_entry_set_text(entry, "")` **before**
`g_strdup(q)`. The copy therefore ran on an emptied buffer. The user's bubble still looked
correct, because it is drawn before the clear — which is exactly why this read for hours as a
model fault, a prompt fault, or a VM fault rather than a shell one.

An empty question matches none of `aurorad`'s fast-path patterns, so it went to the model as
an empty turn, and a 1.5B model given a large system prompt and no user content answered from
the prompt itself: it echoed the example question `how is my machine doing` back as though the
user had asked it. `open a terminal` opened nothing. The defect dates from `ce27fea`, the
commit that first wrote the shell.

Two consequences worth stating plainly. The evaluation numbers were never measuring this: the
harness and every `curl` check POST real text to `/ask`, which is the one path that worked, so
90.8% pipeline accuracy and a completely broken panel were true at the same time. And 129
green tests missed it because nothing exercised the C shell at all.

Confirmed from inside a booted guest before any fix: `POST /ask {"q": ""}` reproduces the
exact echo, `{"q": "open a terminal"}` opens a terminal window, and the md5 of every shipped
Python file plus the sha256 of the bundled model match the repo and the host byte for byte —
so nothing else differed between the guest and a working host.

Fixed in `c0bc249`: the text is owned before the clear and that allocation moves into the job
(`aura_worker` already frees `j->q`, so it is copied once, not twice). `/ask` now answers an
empty question directly instead of asking the model. Two guards were added: one reads
`aurora-shell.c` and fails if the copy moves back after the clear, one drives a live `aurorad`
with a stub model that would run a tool if an empty ask ever reached it again.

### Verified on the fixed image

ISO `daybreakos-2026-09-16-fixed.iso`, 2,087,778,304 bytes, sha256 `99ed9a0c…`, built from
`c0bc249` + `01c057b` with the model bundled and `AURORA_DESKTOP=1` in the autostart so it
boots to the desktop rather than the installer. Six exchanges, all typed into the panel and
observed on screen:

| Typed | Result |
|---|---|
| `hi` | "Hello! How can I help you today?" |
| `open a terminal` | "Opening a terminal." **and a `foot` window opened** |
| `what is a terminal` | an explanation, and no window opened |
| `set brightness to 100` | "This device has no software-controllable backlight." |
| `check ping status for google.com` | "Battery 96% (Not charging); network up; DaybreakOS." |

The brightness answer is read from the hardware rather than invented. The last row is the
weakest: it answered with the generic status line instead of pinging anything, so the
`system_status` fast path matched more loosely than the question deserved. Worth fixing, not
worth blocking on.

### Not verified

- **The animated placeholder.** `Thinking ·` was seen rendered 250 ms after submitting, so the
  new placeholder text reaches the screen. The dots cycling through `· ·` / `· · ·` and the
  elapsed seconds appearing after five were **never captured**: every attempt either caught a
  settled conversation or failed to reach the panel, because once Aura opens a terminal that
  window takes keyboard focus and `keyboardputstring` goes there instead.
- **The honest-error path.** `aura_reply_text` no longer falls back to printing the raw
  response (`g_strndup(json, 400)`); it reports the daemon's `error` field, or says "Aura
  returned something I couldn't read. Nothing was run." No response in this check had an
  unreadable shape, so that branch was never exercised on a booted system.
- **The daemon is served by two `aurorad` processes** (session and root) with `127.0.0.1:7212`
  listening. Note that `pgrep -a aurorad` finds nothing, because the process name is
  `python3`; use `pgrep -af aurorad`.

## Not tested

- The **Aura panel's own buttons**. The four rows in the first table came from `/ask` over
  HTTP; the six in "Verified on the fixed image" were typed into the panel. Neither exercised
  the **Power off** / **Cancel** buttons or the 30-second expiry.
- The **installed system's first-boot model download**, since this ISO bundles the model.
- Anything on **real hardware**. VirtualBox provides no hardware GL, so the desktop runs on
  software rendering here.

## Problems found during the check

Both were in the test harness around the system, not in DaybreakOS:

- The VM was created with a **PS/2 mouse**, a relative pointing device, so VirtualBox captured
  the cursor. Fixed with `--mouse usbtablet` (the guest kernel has `USB_HID`, `HID_GENERIC`
  and `INPUT_EVDEV` built in).
- The VM had **no hard disk**, so the installer correctly reported "No installable disk
  found". Fixed by creating and attaching a 20 GB VDI.
- **Driving the VM by mouse does not work reliably.** Synthetic clicks through
  `SetCursorPos` + `mouse_event` land in the wrong place: the host-to-guest coordinate mapping
  changed between boots of the same VM — host `(-691, -85)` reached guest `(1233, 20)` once and
  `(778, 640)` later — most likely display scaling on that monitor. `Tab` is no escape either:
  it cycles three widgets and never reaches the installer's buttons. What does work is
  `keyboardputstring` / `keyboardputscancode`, `screenshotpng` for observation, and
  `W-Return` (`keyboardputscancode e0 5b 1c 9c e0 db`) to open a terminal. To reach the
  desktop without the installer at all, build with `AURORA_DESKTOP=1` in the labwc autostart:
  `aurora-shell` chooses installer-vs-desktop from `statfs("/")`, and the marker files it
  used to read are dead code the source itself calls a fragile heuristic.
- **Keyboard input goes to whatever holds focus, which is not always the panel.** After Aura
  opens a terminal, that window takes focus, and further `keyboardputstring` calls type into
  it rather than the chat box. This swallowed the attempt to capture the animated placeholder,
  and earlier in the day the reverse happened — the panel took focus and diagnostic commands
  went into the chat box, making a working assistant look broken. Send `echo FOCUS_OK` first
  and confirm where it lands before trusting anything typed afterwards.
- **VirtualBox NAT port-forwarding cannot reach `aurorad` or `llama-server`.** Both bind the
  guest's loopback, not its NAT address, so forwards to 7212 and 8080 connect to nothing.

Several `curl` attempts failed for reasons that were not DaybreakOS's fault and are recorded
here so the transcript is not misread: mangled addresses (`127.0.0.8080`), JSON whose quotes
were stripped in transit (`{"error": "bad json"}`), and one request sent without a
`Content-Type` header, which `aurorad` refused with
`{"error": "requests from web pages are not allowed"}` — the browser-request hardening
behaving exactly as designed.
